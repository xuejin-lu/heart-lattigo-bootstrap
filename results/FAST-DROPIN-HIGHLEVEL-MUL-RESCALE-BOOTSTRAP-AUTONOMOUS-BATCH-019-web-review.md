## Why acceptance is bounded and what to do next

The source-identical production operation chain is real; the Fast-only build-tag capacity adapter is an **observer**, not an application arithmetic constructor. Its presence means measurement/evidence tooling is not byte-identical across builds, while the application public CKKS operation chain is. Native DecryptNew is tested only at Level0 and post-Bootstrap Level1, **not on compact high-Level q0..q3 ciphertexts**. Fast zero-secret is deliberately cryptographically insecure.

This result closes the specific gap left between 016, 017 and 018: high-Level compact `MulRelin/Rescale` now composes with E32 public Bootstrap under one canonical Q/P profile. It does **not** establish all public operand overloads or all Levels, native high-Level compact ciphertext decryption, total memory savings, or realized speedup.

**Next Web-owned priority:** a bounded, reproducible **020 public-chain performance qualification** on the now-passing 019 workload with exact genuine Standard vs Fast pins. Compare fixed-input cheap primitive timings (more than one trial if cost permits) and isolated one-shot Bootstrap time per backend, record RSS/allocations/stage timings separately, control compilation/keygen/diagnostic instrumentation, and never infer statistically stable Bootstrap acceleration from one timed invocation. If low-impact benchmark setup is not feasible without modifying kernels or changing the accepted frontend, stop with a source-backed measurement design instead of running apples-to-oranges tests. Secondary and genuine Standard remain read-only; native high-Level DecryptNew and public overload coverage should be separate later work.
