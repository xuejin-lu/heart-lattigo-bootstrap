# EXP-001 — Standard vs Fast Bootstrap Speed Baseline

## Research question

Measure the end-to-end speed difference between Standard Lattigo and the current Fast-CKKS backend under one fixed CKKS bootstrap workload.

This task answers only:

> Under the same primary frontend, effective parameters, input workload, measurement code, machine, and command, how much faster is Fast than Standard for one complete bootstrap?

Do not optimize Fast, do not add stage profiling, and do not begin noise experiments in this task.

## Fixed repositories

Primary experiment harness:
- `xuejin-lu/heart-lattigo-bootstrap`
- use the synchronized `main` commit that contains this task; do not edit the primary source/config between Standard and Fast measurements.

Secondary backend repository:
- `xuejin-lu/lattigo`

For this EXP-001 baseline, do not use moving branch tips as the experimental identity. Fetch remote refs, then test these exact commits:

## Backend switching procedure

Codex must switch the sibling `../lattigo` checkout automatically. The user should not manually checkout backends.

Use a clean detached-HEAD measurement flow so no backend branch is modified:

### Run A — Standard

1. In `../lattigo`, checkout the pinned Standard commit in detached HEAD:
   `git switch --detach 5dbffbdea05394de2ca3a432ed5318aa832e3f40`
2. Verify `git status --short` is empty.
3. Verify `git rev-parse HEAD` equals the pinned Standard SHA.
4. Return to Primary without changing any primary source/config.
5. Run the fixed experiment command and save a Standard result JSON.

### Run B — Fast

1. In `../lattigo`, checkout the pinned Fast commit in detached HEAD:
   `git switch --detach d5429b1c368a6828ef1bb8a229e3f57458ad6491`
2. Verify `git status --short` is empty.
3. Verify `git rev-parse HEAD` equals the pinned Fast SHA.
4. Return to Primary without changing any primary source/config.
5. Run the exact same experiment command and save a Fast result JSON.

### Restore

After both runs, restore the original secondary branch/ref recorded before the experiment, but only if the worktree is still clean. If restoration would overwrite or conflict with new work, stop and report instead.

Do not commit anything to `lattigo` in EXP-001.

```text
  -config configs/bootstrap_config.example.json \
  -repetitions=10 \
  -warmup=3 \

```

Recommended outputs:

```text

```

Do not edit `configs/bootstrap_config.example.json` between runs.

## Workload identity

This experiment uses the current EXP-000 compatibility workload:

- `ModUpThenEncode`
- parameters are generated by the active Lattigo public bootstrapping builder
- Standard and Fast must report identical `effective_parameters` in result JSON

Important historical note:

This compatibility workload is not claimed to be byte-for-byte or construction-for-construction identical to the legacy hardware repository's old `DecodeThenModUp` parameter builder. The fairness claim in EXP-001 is Standard vs Fast under the same current effective workload, not equivalence to the old hardware-model baseline.

## Measurement boundary

Use the existing harness measurement boundary unless a correctness bug is found:

- parameter construction: outside timed bootstrap repetitions
- key generation: outside timed bootstrap repetitions
- evaluator construction: outside timed bootstrap repetitions
- warm-up: outside recorded measurements
- reproducible ciphertext input construction: outside the timed `Bootstrap` call
- complete `eval.Bootstrap(ct)`: timed

Do not change this boundary between Standard and Fast.

## Required result checks

Before calculating speedup, verify:

1. Primary commit is identical in both JSON results.
2. Effective parameters are identical in both JSON results.
3. Config is identical in both JSON results.
4. OS / architecture / CPU metadata are identical.
5. Repetition and warm-up counts are identical.
6. Standard result records Lattigo commit `5dbffbdea05394de2ca3a432ed5318aa832e3f40`.
7. Fast result records Lattigo commit `d5429b1c368a6828ef1bb8a229e3f57458ad6491`.
8. Every measured bootstrap succeeds and produces the expected output level.

If any identity check fails, do not report a speedup number. Fix or report the mismatch first.

## Summary statistics

From the 10 measured complete-bootstrap repetitions for each backend, report at least:

- median elapsed time per bootstrap
- mean elapsed time per bootstrap
- min and max elapsed time
- median allocation bytes per bootstrap
- median allocation count per bootstrap
- Fast speedup using median time:

```text
speedup = Standard median elapsed / Fast median elapsed
```

Prefer median as the headline speedup because it is less sensitive to one noisy run.

Do not add stage timing in this task.
