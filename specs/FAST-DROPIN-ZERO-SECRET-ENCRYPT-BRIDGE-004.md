## Frozen zero-secret algebra

For a newly encoded CKKS plaintext `pt`, the Fast simulation-facing public `rlwe.NewEncryptor(ckksParams, key).EncryptNew(pt)` must produce the *same logical ciphertext type* with degree one, `c0 = pt` in its ring representation and `c1=0` (all active rows), preserving the ciphertext/public plaintext metadata (level, Scale, IsNTT, IsMontgomery, slots, dimensions). The backend is **intentionally insecure numerical simulation**, not native RLWE encryption. Preserve correct ring representation; do not assume `pt` is always NTT or always Level 0.

Why: zero-secret decryption is `c0 + c1*0 = c0`; the original frontend's specified plaintext must survive before Fast Bootstrap. **Never** convert a normally encrypted nonzero-c1 ciphertext by simply zeroing c1, never decrypt internally using the frontend's secret as a hidden bridge, and never claim that the CKKS SecretKey object is literally zero if it is still sampled. Treat sampled keys as externally present but irrelevant to this simulated ciphertext's meaning.

The public `rlwe.NewDecryptor(ckksParams, sk).DecryptNew(ct)` must return the intended plaintext when Fast input/output has c1=0. If an operation produces nonzero c1, investigate and explicitly enforce a valid Fast output invariant or report `NEEDS_WEB_REVIEW`; do **not** silently mask/ignore a nonzero component or reinterpret ciphertext from native Standard. The implementation must correctly isolate Fast simulation by **CKKS parameter/provider provenance** without importing `schemes/ckks` from `core/rlwe` or otherwise creating an import cycle. A typed internal/provider capability interface with a Fast-only CKKS opt-in may be considered; alternative minimal design allowed if source-proven. Do not globally change ordinary RLWE, BFV, BGV or other scheme encryption semantics, and do not require the frontend to pass a new flag or constructor.

Scope focus: secret-key-based `EncryptNew` and the ordinary CKKS lifecycle only. Public-key encryption, serialization interoperability across Standard and Fast, multi-operation arbitrary workloads and Fast key-generation cost are deferred; report clearly rather than silently claiming support. If existing CKKS consumers in Fast fork need an explicit Standard crypto path, preserve their behavior where feasible or report precise tests/conflict instead of broad unchecked change.
