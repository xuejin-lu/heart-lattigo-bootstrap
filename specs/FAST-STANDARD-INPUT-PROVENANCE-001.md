## Scientific input contract (do not reinterpret)

1. **Same underlying message**: use existing `perfmeasure.DeterministicInput` vectors and frozen `configs/bootstrap_config.logN13.json` / `configs/bootstrap_config.logN16.json`. Check the same original-vector SHA-256, actual Q/P prime *values*, LogN, LogSlots, scale, circuit order and effective profile within each backend pair. LogN13 and LogN16 need not match each other. Do not tune the parameters or relax numeric gates.
2. **Standard — native lifecycle only**: create the genuine Standard secret key (and evaluation keys as needed); encode the message into an appropriate native Standard plaintext; encrypt using Standard `rlwe.NewEncryptor(..., valid Standard key).EncryptNew(pt)` or the pinned source's equivalent public API; decrypt with the *same matching* Standard secret key and decode. Use a fresh Standard key/encryption for every independent numerical trial. Never assemble a Standard ciphertext by copying encoded plaintext into `c0`, zeroing `c1`, copying a Fast ciphertext, reinterpreting metadata, or otherwise bypassing encryption. Do not edit the pinned Standard library, its key generator, arithmetic, or cryptographic constructors to make this work.
3. **Fast — explicit intentionally insecure input model**: for this research stage, the only source-backed starting candidate is the existing Fast-specific encoded zero-secret/zero-a input (`c0=encoded message,c1=0`) used by Fast Bootstrap's test helper. It may be used **only in the Fast adapter**, with a conspicuous input kind such as `fast_zero_secret_direct_encoded_v1`, and described as an intentional simulation/zero-a model, **not** native encryption, a secure ciphertext, or security-equivalent to Standard. Confirm it satisfies the pinned Fast public Bootstrap entry contract and round-trip decoding. Do not attempt to pass a `KeyLayoutFast` public key to the ordinary RLWE encryptor or remove its safety rejection. If source inspection or focused test evidence fails to justify even this bounded Fast simulation input, stop with `NEEDS_WEB_REVIEW` rather than inventing a Fast-encryption protocol.
4. **Independent input identities**: identical original message hash and effective parameters are required; identical ciphertext contents, `c1`, ciphertext metadata SHA, key bytes, or randomness are **not** required and should not be enforced. Report provenance separately for each backend and Standard trial. Never serialize secret keys.
5. **Input quality**: for each constructed input, decode under that backend's declared semantics **before** Bootstrap and compare to the original vector. Require finite decoded values, correct slot count/metadata/level and a maximum per-complex-slot input deviation of at most `1e-6` for this fixed canonical input/profile. Treat this threshold as a mandatory preflight failure, not as a tweakable performance or output-accuracy target. If the target is impossible under the pinned Standard API, stop and report precise evidence for Web scientific review; do not adjust it silently.
6. **Claim boundary**: successful Fast simulation plus genuine Standard encryption supports a comparison of **genuine Standard Bootstrap computation versus the explicitly insecure Fast-Q-prefix simulator** under the same message/profile. It does **not** prove security equivalence, equivalent encrypted-input noise, or normal Fast public-key encryption. Each backend's future output should be evaluated versus the original message as well as, secondarily, against the other backend, and with the proper limitations.
